Rosetta Canonical Model

One canonical projection over every agent's ground truth — ten entities, checked against the nine captured groundtruth.json packs (gemini and cursor pending). Sessions group under projects, transcripts flatten into typed timeline rows, native tool dialects collapse into user-facing semantic actions, and heavy aggregates live in materialized caches updated at ingest.

Implementation checkpoint · 2026-08-30. All ten logical entities are implemented across nine captured-agent adapters. The runtime drives adapter-selected JSONL, bounded rewrite-in-place document snapshots, and SQLite snapshots. Projection schema 12 includes replacement-keyed session_usage for native totals that cannot be attributed to one response, deterministic metadata evidence ties, RAM-only replacement staging, and canonical/search epoch-revision state. Fresh serve commits to a public, resumable WAL projection; finite ingest and whole-ledger rebuild validate privately before atomic installation. Verified inline images are decoded into content-addressed projection members; message rows retain stable service URLs and the raw ledger remains lossless. FTS5 is a detached disposable generation built asynchronously after canonical validation, then repaired from a coalesced session set. Ordinary schema mismatches fail closed. The in-process hot tier, subscription hub, HTTP/WebSocket transport, and generated clients exist. Each adapter settles one primary session cwd and optional repository/project during bounded metadata admission; stream records cannot revise ownership. Schema 12 ships the strict message/tool contract below and contains no workspace-observation relation. Native tool objects, progressive snapshots, and reconciliation bookkeeping remain ledger/RAM-only; SQLite contains only the resolved user-facing action. Message rows — the flattened taxonomy

One block per row, tool results merged into their tool_use row. Most agents are already flat; claude-code is the one that packs blocks inside assistant messages, and the split transform un-packs it to match everyone else. Native role labels are evidence, not authority: a source row called user is canonical user prose only when it was authored by the human.

The canonical message boundary

The raw ledger is the complete forensic record. The canonical projection is the user-facing explanation of what happened. A native object is therefore not canonical merely because it parsed successfully.

Measured reason to close the gap. After inline images were externalized, the audited Claude transcript still held 14.67 MiB of classified message text. Read, Edit, Bash, and Write accounted for 12.60 MiB (85.9%); literal duplicate input/result/payload pairs accounted for about 5.7 MiB. The three tool columns alternated between plain text, JSON objects, JSON encoded as strings, and null. Those values are both storage waste and an impossible presentation contract. The source evidence is recorded in message-payload-weight.html and message-schema-matrix.html.

Roster-wide structural audit · 2026-08-29. A privacy-safe, point-in-time scan of the nine installed runtimes classified 377,877 tool calls. The draft mapping covered 65.46% overall and 99.65% after excluding Codex's opaque outer exec envelope. Claude, Codex, and Grok alone carried 2.79 GiB of native tool-result values, validating the reduction boundary, but the scan also disproved four assumptions: every call has a native id, every lifecycle has only start/completion, every writer exposes a human turn/response boundary, and every required action identity is available in the request. These are structural observations, not a frozen performance campaign; they block activation and define the amendments below.
LEDGER IS COMPLETERaw bytes, checksums, unknown fields, successful command output, and dropped tool bodies remain replayable.
PROJECTION ANSWERS USERSKeep the target, intent, state change, outcome status, and user-authored content. Discard transport and model-context noise.
NO NATIVE JSON ESCAPE HATCHAdapters construct Rust variants. Core and protocol expose generated discriminated unions, never serde_json::Value.
NARROWING NEVER BLOCKS INGESTUnfamiliar shapes become a bounded unknown action plus drift evidence; the record still commits.

The public wire contract is an envelope plus a closed body union. The source's role string cannot select a variant by itself: adapters must establish who authored prose and whether a machine record is a tool completion, notice, summary, or ledger-only context.

Content invariant: prose is human-readable text, never serialized JSON. A user row has text or at least one attachment; an agent row has text, an attachment, or a citation. This permits attachment-only messages without fabricating an empty string. Empty/redacted thinking remains ledger-only. A native record named attachment is not an attachment by label: authorship and its typed fields must prove user-visible media or a document reference.

Identity invariant: one logical tool call produces one row keyed by the adapter's deterministic correlation key. A native id is retained when reported but is never required. Native, parent-linked, positional, and synthetic correlation are distinguishable. Likewise every row belongs to a deterministic causal group, but only kind = human_turn claims a human turn; response grouping is optional and carries its derivation. Clients may group synthetic rows but may not present them as exact provider boundaries.

Fact-preservation invariant: dropping an empty block, progress body, or machine wrapper never drops its usage/model/timing fact. Response-owned facts reattach to the response when that relationship is proven and otherwise become replacement-keyed session_usage. Completion and progress may update only typed fields and can never attach a native result blob.

One-diff rule. For each changed path, prefer a native post-execution patch that describes the actual change; otherwise derive a unified diff from verified old/new values, or a create/delete diff from the one available body. Normalize headers and line endings deterministically, compute line counts from that same diff, then discard every old/new/original/content/ hunk copy. A whole-file write with only one body may yield a create/delete-shaped diff, but that shape does not prove whether the operation created or overwrote the path. If the source cannot prove an operation or diff, retain the path and independently known counts with the corresponding field absent; never relabel a whole file or acknowledgement as a diff.
Shell-output decision. Successful stdout and stderr are never canonical. For failed, denied, interrupted, or timed-out actions, the normalizer may retain a typed failure and at most 4 KiB / 40 lines of deterministic diagnostic text, preferring structured error or stderr. This is the only command-output exception; it explains a failure without recreating a terminal archive. The UI keeps it collapsed.
Status is evidence, not sentiment. Each registration declares whether native state, a terminal record, or a ground-truth protocol contract proves a status. Output existence means success only when the pinned writer contract says so; text sniffing never does. Source finalization may turn a still-open call into unknown, never succeeded. A newer, higher-ranked native snapshot may correct an older fact; sparse updates cannot erase proven fields.

Storage and search contract for typed messages

SQLite may store a typed union as JSON text; the escape hatch is the producer type, not the SQL affinity. Only a closed Rust enum can serialize detail. Store reads deserialize it back into that enum, and the generated protocol returns the same discriminated union. No adapter, query, or client receives a generic JSON value. A content member is written to a private name, verified, and durably renamed before the referencing row commits; search resolves full member text only after that commit. The member is part of the same disposable projection, not a third source of truth.

Every mutation is idempotent by correlation key plus evidence order. Out-of-order updates wait only in a process-local RAM map; no update fragment or native JSON is serialized to SQLite. Missing fields never clear earlier facts. A higher-ranked or later equally ranked fact may enrich or correct one field according to the registration's documented precedence. The store rejects known-family changes, except that unknown may upgrade once to the registry-selected family when a progressive request establishes its typed identity. Repeated snapshots therefore converge to one row instead of producing duplicates.

The non-serializable RAM fold may track an evidence winner per approved canonical field while it resolves one batch. That bookkeeping is discarded after the resolved row commits. This lets an older out-of-order patch fill a missing field without overwriting a newer value, while the raw ledger—not a second SQLite fact journal—reconstructs the same fold after restart.

Unsupported update shapes omit only their unfamiliar facts and emit drift; they never erase a typed request. A live call may remain pending/running. When an authoritative source generation ends without terminal evidence, source finalization changes it to unknown, not succeeded. An update that never finds an opener becomes drift plus ledger provenance rather than a fabricated timeline row.

Unknown and drift policy

A raw parser remains permissive. The adapter then attempts a named semantic projector. Unknown extra fields are drift, not a reason to discard already-proven semantic fields. If a known request can establish its family or any independently useful identity, its typed action survives even when another requested fact is absent or the completion shape is new: unprovable fields remain absent, reliable status/timing still merge, the unfamiliar outcome is omitted, and drift points to the ledger sample. ToolAction::Unknown is reserved for an unregistered namespace/name or a record that the versioned projector cannot yet classify. A progressive request may upgrade that row once to the registry-selected known family; it may never oscillate between families.

Either path increments an aggregated projection_unknown drift fact keyed by runtime/writer-version/namespace/name/phase/shape hash and records one bounded ledger sample reference. It never stores the rejected object, invents a user-facing field, erases an earlier typed request, or aborts the record, session, or batch. Once a projector is added and its normalizer version bumps, replay recovers the richer action from the ledger.

Parse & write strategy — discover, meta ingest, stream

Phase 1 finds what's installed so the app can ask what to ingest. Phase 2 makes every list render within seconds. Phase 3 commits canonical transcript and rollup state per file; once the canonical gate passes, a detached search worker builds an independently published FTS5 generation while lists and timelines remain available.

1 · Discovery

The layout manifests probe each candidate data root: which agents exist, their versions, roughly how much data. Nothing else is read — discovery exists so the app can show what it found and ask which agents to ingest. The selection persists, and re-running is cheap enough to spot a newly installed agent at any time.

2 · Meta ingest

Small synchronous transactions, recency-ordered (mtime descending) so current work lands first. stat calls give the session list and timestamps; bounded reads — opening records and tiny metadata documents/databases — fill titles and settle one primary cwd plus optional repository project. Plans and tasks may also be admitted from bounded metadata. Project and session lists render now; each session shows an indexing state until its stream lane catches up.

3 · Stream lanes

Writes funnel through one canonical writer with batched commits. Message rows, rollup corrections, checkpoints, and coalesced search-repair keys commit in the same transaction; detached FTS generations never share that transaction. Aggregates cannot drift, and cumulative→delta normalization (the codex trap) happens here, once. Priority: live tails first, then sessions the user opens, then newest-first backfill. Everything resumes via ingest_cursor (a versioned driver checkpoint: generation · file identity · committed offset · boundary anchor) — the simplest form of the pattern codex itself ships as next_rollout_byte_offset. The live lane is memory-first: active sessions keep an in-process tail ring that serves the realtime view ahead of the batched commit — the DB is structurally behind the tail, so this is correctness, not optimization (design: ingest-engine.html, "The hot tier").

-- session grain ONLY: project / runtime / all-time totals are query-time sums
-- through the session's metadata-settled ownership.
-- replacement-aware: usage keys to its response row or session_usage.sample_key; a re-reported snapshot
-- applies (new − old) to the bucket in the same tx as the row update

CREATE VIEW session_contribution AS    -- one row per ROOT session: subagent trees fold in
SELECT r.id AS session_id, r.project_id,
       COALESCE(u.tokens, 0)  AS tokens,
       COALESCE(g.commits, 0) AS commits,
       COALESCE(f.edits, 0)   AS edits,
       COALESCE(f.loc, 0)     AS loc
FROM session r
LEFT JOIN (SELECT s.root_session_id rid,
                  SUM(b.in_tokens + b.out_tokens + b.cache_r_tokens
                      + b.cache_w_tokens + b.think_tokens) tokens
           FROM usage_bucket b JOIN session s ON s.id = b.session_id
           GROUP BY rid) u ON u.rid = r.id
LEFT JOIN (SELECT s.root_session_id rid, COUNT(*) commits
           FROM git_commit g JOIN session s ON s.id = g.session_id
           GROUP BY rid) g ON g.rid = r.id
LEFT JOIN (SELECT s.root_session_id rid, COUNT(*) edits,
                  SUM(COALESCE(f.lines_added, 0) + COALESCE(f.lines_removed, 0)) loc
           FROM file_edit f JOIN session s ON s.id = f.session_id
           GROUP BY rid) f ON f.rid = r.id
WHERE r.id = r.root_session_id;

Every canonical table has a named correctness or product consumer; the detached search schema has one worker and one query backend. Live-lane updates touch message, session.updated_at, and the buckets through the same single-writer funnel as backfill.

Two usage features, two queries

The rethought cache exists so these service-level features are trivial reads — no feature-specific tables, just sums over usage_bucket and friends.

Activity heatmap

GitHub-style day grid for a project, a session, or everything — grouped into the viewer's timezone at query time, which only works because the buckets are hourly. The same table answers hour-of-day profiles (when do you actually work?) with a different GROUP BY.

SELECT date((b.hour_ts + :utc_offset_ms) / 1000, 'unixepoch') AS day,
       SUM(b.in_tokens + b.out_tokens + b.think_tokens
           + b.cache_r_tokens + b.cache_w_tokens) AS tokens
FROM usage_bucket b
JOIN session s ON s.id = b.session_id
WHERE s.project_id = :project AND b.hour_ts >= :since
GROUP BY day;

Contribution board

Sessions ranked by what they added to a project — tokens, commits, edits, or LOC, all sortable columns of one view. Subagent trees fold into the session the user actually ran; the per-subagent breakdown stays one query away via root_session_id.

SELECT * FROM session_contribution
WHERE project_id = :project
ORDER BY tokens DESC;   -- or commits · edits · loc
