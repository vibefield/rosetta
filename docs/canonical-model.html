Rosetta Canonical Model

One canonical projection over every agent's ground truth — eleven entities, checked against the nine captured groundtruth.json packs (gemini and cursor pending). Sessions group under projects, transcripts flatten into typed timeline rows, native tool dialects collapse into user-facing semantic actions, and heavy aggregates live in materialized caches updated at ingest.

Implementation checkpoint · 2026-08-29. All eleven logical entities are implemented across nine captured-agent adapters. The runtime drives adapter-selected JSONL, bounded rewrite-in-place document snapshots, and SQLite snapshots. Projection schema 7 includes replacement-keyed session_usage for native totals that cannot be attributed to one response, deterministic metadata evidence ties, generation-scoped source_op replacement staging, and canonical/search epoch-revision state. Fresh serve commits to a public, resumable WAL projection; finite ingest and whole-ledger rebuild validate privately before atomic installation. Verified inline images are decoded into content-addressed projection members; message rows retain stable service URLs and the raw ledger remains lossless. FTS5 is a detached disposable generation built asynchronously after canonical validation, then repaired from a coalesced session set. Ordinary schema mismatches fail closed. The in-process hot tier, subscription hub, HTTP/WebSocket transport, and generated clients exist. Schema 7 still stores native tool input, result, and payload opaquely. The strict message/tool contract below is the ratified target for the next projection schema; it is not yet the shipped wire or SQLite shape. The full adapter/visibility audit is in ADAPTER_AUDIT.md.

Message rows — the flattened taxonomy

One block per row, tool results merged into their tool_use row. Most agents are already flat; claude-code is the one that packs blocks inside assistant messages, and the split transform un-packs it to match everyone else. Native role labels are evidence, not authority: a source row called user is canonical user prose only when it was authored by the human.

The canonical message boundary

The raw ledger is the complete forensic record. The canonical projection is the user-facing explanation of what happened. A native object is therefore not canonical merely because it parsed successfully.

Measured reason to close the gap. After inline images were externalized, the audited Claude transcript still held 14.67 MiB of classified message text. Read, Edit, Bash, and Write accounted for 12.60 MiB (85.9%); literal duplicate input/result/payload pairs accounted for about 5.7 MiB. The three tool columns alternated between plain text, JSON objects, JSON encoded as strings, and null. Those values are both storage waste and an impossible presentation contract. The source evidence is recorded in message-payload-weight.html and message-schema-matrix.html.
measured payload classaudited bytescanonical treatment
Read content copies3.91 MiBdrop raw and numbered bodies; keep path/range
Edit old/new/original/patch copies3.53 MiBderive one unified diff per changed path; discard every source copy
Bash output1.88 MiBdrop successful output; failure-only diagnostic is hard-bounded
Bash command0.39 MiBkeep once as command intent

This is evidence from one large Claude file, not a roster-wide savings forecast. The action contract is roster-wide; byte and time claims require a frozen before/after ledger campaign.

The public wire contract is an envelope plus a closed body union. The source's role string cannot select a variant by itself: adapters must establish who authored prose and whether a machine record is a tool completion, notice, summary, or ledger-only context.

Invariant: user/agent/summary text is human-readable text, never serialized JSON. Empty or redacted thinking does not create a timeline row. Tool starts and completions merge by native id into one ToolInteraction; completion can change status, timing, failure, and the typed action's outcome, but cannot attach a native result blob. Every row has a deterministic turn id; agent, thinking, and tool rows also have a deterministic response id and block index, synthesized from native response boundaries when the source does not supply them. Dropping an empty/redacted block or machine wrapper never drops its usage/model/timing fact: response-owned facts reattach to the response, and otherwise become replacement-keyed session_usage.

One-diff rule. For each changed path, prefer a native post-execution patch that describes the actual change; otherwise derive a unified diff from verified old/new values, or a create/delete diff from the one available body. Normalize headers and line endings deterministically, compute line counts from that same diff, then discard every old/new/original/content/ hunk copy. If the source cannot prove a diff, retain path + operation + known counts with diff = None; never relabel a whole file or acknowledgement as a diff.
Shell-output decision. Successful stdout and stderr are never canonical. For failed, denied, interrupted, or timed-out actions, the normalizer may retain a typed failure and at most 4 KiB / 40 lines of deterministic diagnostic text, preferring structured error or stderr. This is the only command-output exception; it explains a failure without recreating a terminal archive. The UI keeps it collapsed.

File and directory paths resolve lexically against the adapter's timestamped cwd when available; normalization never touches the live filesystem or follows symlinks. If cwd is unknown, the source spelling is retained with resolved = false rather than guessed.

NO SILENT LOSS OF IMPORTANT TEXTCommands, diffs, collaboration bodies, structured answers, and user/agent prose cross the inline limit by becoming immutable content-addressed members, not by truncation.
BOUNDED COLLECTIONSSearch locations and tool names: 20. Web sources: 10. External display fields: 24. Every reduced list also stores total_count. Canonical documents over 32 KiB become typed members instead of losing blocks or rows.
BOUNDED EXTERNAL VALUESRegistry fields are scalar or flat scalar lists; labels are 128 bytes, strings 1 KiB, lists 20 values. No arbitrary nesting crosses the boundary.
BOUNDED CORE SCALARSIds/names are at most 512 bytes; path, URL, query, subject, option, and other scalar fields are at most 16 KiB. Overflow makes the action unknown + drift instead of saving a misleading truncation.
DETERMINISTIC REDUCTIONUTF-8 boundaries, list ordering, diagnostic selection, diff generation, and previews are pure/versioned. Same ledger + version produces byte-identical rows.

CanonicalDocument is a narrow exception, not a payload wrapper. It is legal only for a tool whose declared product is a user-visible structured answer. Its converter emits the fixed field/list/table/section tree above, externalizes binary members, and drops schema/debug wrappers. Core validation rejects attempts to place a native tool request, response, or arbitrary object inside it. Registered external actions are stricter: only their reviewed scalar fields and resources cross the boundary.

One semantic role, one value. If native fields repeat the same meaning across request/result/payload, the projector applies a documented precedence and stores one. For delegation and workflows, prefer an explicit description/summary over the full prompt; use the prompt only as the fallback objective. For result-derived facts, prefer the post-execution value over the requested value.

Distilled entities remain authoritative. The same native record may emit a minimal timeline action plus a canonical task, plan, file_edit, child-session link, artifact member, or derived commit. A tool card keeps the small identity/snapshot needed to explain the event; full task lists, plan bodies, edit source copies, and child transcripts belong to their named entity or the ledger, never a hidden payload.

Storage and search contract for typed messages

SQLite may store a typed union as JSON text; the escape hatch is the producer type, not the SQL affinity. Only a closed Rust enum can serialize detail. Store reads deserialize it back into that enum, and the generated protocol returns the same discriminated union. No adapter, query, or client receives a generic JSON value. A content member is written to a private name, verified, and durably renamed before the referencing row commits; search resolves full member text only after that commit. The member is part of the same disposable projection, not a third source of truth.

Unknown and drift policy

A raw parser remains permissive. The adapter then attempts a named semantic projector. Unknown extra fields are drift, not a reason to discard already-proven semantic fields. If a known request can establish its required identity (for example Bash command or Read path), its typed action survives even when the completion shape is new: independently reliable status/timing still merge, the unfamiliar outcome is omitted, and drift points to the ledger sample. ToolAction::Unknown is reserved for an unregistered tool or a request whose minimum identity cannot be established.

Either path increments an aggregated projection_unknown drift fact keyed by runtime/version/name/phase/shape hash and records one bounded ledger sample reference. It never stores the rejected object, invents a user-facing field, erases an earlier typed request, or aborts the record, session, or batch. Once a projector is added and its normalizer version bumps, replay recovers the richer action from the ledger.

Activation gate

1 · Prove the projectors

Add typed fixture cases for every mapped family in every captured adapter. Differential replay must show no user/agent prose loss, one tool row per call, deterministic ids/order, and only declared fields crossing the boundary.

2 · Prove reduction

On one frozen checksummed ledger, assert that Read contents, successful shell output, whole-file copies, native payload keys, and exact duplicate pairs are absent from SQLite and FTS. Report DB/member/FTS bytes by semantic family plus normalize, canonical-apply, search-build, whole-wall, and peak-RSS deltas from the paired run; estimates do not count.

3 · Prove product behavior

Generated TypeScript must contain no generic tool JSON. The timeline renders all variants without native-key sniffing; search fixtures prove each allowlisted semantic field and exclude every discarded field. Human/assistant prose queries retain their hit identities; tool-noise queries are intentionally re-baselined rather than forced to match schema 7's ranking digest.

4 · Activate atomically

Land common types, all nine adapter projectors, store/search consumers, protocol, client, and schema-version fail-closed behavior before publishing the new projection. Rebuild privately from the unchanged ledger; do not migrate schema 7 rows.

Activation is a reviewed canonical/search semantics change, not a performance-only optimization: the new allowlist and exclusion oracle must be approved explicitly. After that baseline is frozen, every optimization inside the new schema again requires equal logical counts and ranked digests under the repository's ordinary campaign rule.

Parse & write strategy — discover, meta ingest, stream

Phase 1 finds what's installed so the app can ask what to ingest. Phase 2 makes every list render within seconds. Phase 3 commits canonical transcript and rollup state per file; once the canonical gate passes, a detached search worker builds an independently published FTS5 generation while lists and timelines remain available.

1 · Discovery

The layout manifests probe each candidate data root: which agents exist, their versions, roughly how much data. Nothing else is read — discovery exists so the app can show what it found and ask which agents to ingest. The selection persists, and re-running is cheap enough to spot a newly installed agent at any time.

2 · Meta ingest

Small synchronous transactions, recency-ordered (mtime descending) so current work lands first. stat calls give the session list and timestamps; bounded reads — first and last transcript lines plus tiny sidecars — fill titles, project assignment, plans, and tasks. Project and session lists render now; each session shows an indexing state until its stream lane catches up.

3 · Stream lanes

Writes funnel through one canonical writer with batched commits. Message rows, rollup corrections, checkpoints, and coalesced search-repair keys commit in the same transaction; detached FTS generations never share that transaction. Aggregates cannot drift, and cumulative→delta normalization (the codex trap) happens here, once. Priority: live tails first, then sessions the user opens, then newest-first backfill. Everything resumes via ingest_cursor (a versioned driver checkpoint: generation · file identity · committed offset · boundary anchor) — the simplest form of the pattern codex itself ships as next_rollout_byte_offset. The live lane is memory-first: active sessions keep an in-process tail ring that serves the realtime view ahead of the batched commit — the DB is structurally behind the tail, so this is correctness, not optimization (design: ingest-engine.html, "The hot tier").

CREATE VIEW session_contribution AS    -- one row per ROOT session: subagent trees fold in
SELECT r.id AS session_id, r.project_id,
       COALESCE(u.tokens, 0)  AS tokens,
       COALESCE(g.commits, 0) AS commits,
       COALESCE(f.edits, 0)   AS edits,
       COALESCE(f.loc, 0)     AS loc
FROM session r
LEFT JOIN (SELECT s.root_session_id rid,
                  SUM(b.in_tokens + b.out_tokens + b.cache_r_tokens
                      + b.cache_w_tokens + b.think_tokens) tokens
           FROM usage_bucket b JOIN session s ON s.id = b.session_id
           GROUP BY rid) u ON u.rid = r.id
LEFT JOIN (SELECT s.root_session_id rid, COUNT(*) commits
           FROM git_commit g JOIN session s ON s.id = g.session_id
           GROUP BY rid) g ON g.rid = r.id
LEFT JOIN (SELECT s.root_session_id rid, COUNT(*) edits,
                  SUM(COALESCE(f.lines_added, 0) + COALESCE(f.lines_removed, 0)) loc
           FROM file_edit f JOIN session s ON s.id = f.session_id
           GROUP BY rid) f ON f.rid = r.id
WHERE r.id = r.root_session_id;

Activity heatmap

GitHub-style day grid for a project, a session, or everything — grouped into the viewer's timezone at query time, which only works because the buckets are hourly. The same table answers hour-of-day profiles (when do you actually work?) with a different GROUP BY.

SELECT date((b.hour_ts + :utc_offset_ms) / 1000, 'unixepoch') AS day,
       SUM(b.in_tokens + b.out_tokens + b.think_tokens
           + b.cache_r_tokens + b.cache_w_tokens) AS tokens
FROM usage_bucket b
JOIN session s ON s.id = b.session_id
WHERE s.project_id = :project AND b.hour_ts >= :since
GROUP BY day;
