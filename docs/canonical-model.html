Rosetta Canonical Model

One canonical projection over every agent's ground truth — eleven entities, checked against the nine captured groundtruth.json packs (gemini and cursor pending). Sessions group under projects, transcripts flatten into typed timeline rows, and heavy aggregates live in materialized caches updated at ingest.

Implementation checkpoint · 2026-08-29. All eleven logical entities are implemented across nine captured-agent adapters. The runtime drives adapter-selected JSONL, bounded rewrite-in-place document snapshots, and SQLite snapshots. Projection schema 7 includes replacement-keyed session_usage for native totals that cannot be attributed to one response, deterministic metadata evidence ties, generation-scoped source_op replacement staging, and canonical/search epoch-revision state. Fresh serve commits to a public, resumable WAL projection; finite ingest and whole-ledger rebuild validate privately before atomic installation. Parse & write strategy — discover, meta ingest, stream

Phase 1 finds what's installed so the app can ask what to ingest. Phase 2 makes every list render within seconds. Phase 3 commits canonical transcript and rollup state per file; once the canonical gate passes, a detached search worker builds an independently published FTS5 generation while lists and timelines remain available.

1 · Discovery

The layout manifests probe each candidate data root: which agents exist, their versions, roughly how much data. Nothing else is read — discovery exists so the app can show what it found and ask which agents to ingest. The selection persists, and re-running is cheap enough to spot a newly installed agent at any time.

2 · Meta ingest

Small synchronous transactions, recency-ordered (mtime descending) so current work lands first. stat calls give the session list and timestamps; bounded reads — first and last transcript lines plus tiny sidecars — fill titles, project assignment, plans, and tasks. Project and session lists render now; each session shows an indexing state until its stream lane catches up.

3 · Stream lanes

Writes funnel through one canonical writer with batched commits. Message rows, rollup corrections, checkpoints, and coalesced search-repair keys commit in the same transaction; detached FTS generations never share that transaction. Aggregates cannot drift, and cumulative→delta normalization (the codex trap) happens here, once. Priority: live tails first, then sessions the user opens, then newest-first backfill. Everything resumes via ingest_cursor (a versioned driver checkpoint: generation · file identity · committed offset · boundary anchor) — the simplest form of the pattern codex itself ships as next_rollout_byte_offset. The live lane is memory-first: active sessions keep an in-process tail ring that serves the realtime view ahead of the batched commit — the DB is structurally behind the tail, so this is correctness, not optimization (design: ingest-engine.html, "The hot tier").

The SQLite projection

The canonical model as a compact DDL excerpt — one WAL database, grouped by the ingest phase that fills each table. Search has its own disposable SQLite generation. Ids are blake3 hex, times are unix milliseconds, and structured values are JSON text. Both projections rebuild from canonical rows or the ledger; only the ledger is precious.

PRAGMA journal_mode = WAL;
PRAGMA synchronous  = NORMAL;
PRAGMA foreign_keys = ON;

-- session grain ONLY: project / runtime / all-time totals are query-time sums
-- through session — nothing to invalidate when a session is reassigned.
-- replacement-aware: usage keys to its response row or session_usage.sample_key; a re-reported snapshot
-- applies (new − old) to the bucket in the same tx as the row update

CREATE VIEW session_contribution AS    -- one row per ROOT session: subagent trees fold in
SELECT r.id AS session_id, r.project_id,
       COALESCE(u.tokens, 0)  AS tokens,
       COALESCE(g.commits, 0) AS commits,
       COALESCE(f.edits, 0)   AS edits,
       COALESCE(f.loc, 0)     AS loc
FROM session r
LEFT JOIN (SELECT s.root_session_id rid,
                  SUM(b.in_tokens + b.out_tokens + b.cache_r_tokens
                      + b.cache_w_tokens + b.think_tokens) tokens
           FROM usage_bucket b JOIN session s ON s.id = b.session_id
           GROUP BY rid) u ON u.rid = r.id
LEFT JOIN (SELECT s.root_session_id rid, COUNT(*) commits
           FROM git_commit g JOIN session s ON s.id = g.session_id
           GROUP BY rid) g ON g.rid = r.id
LEFT JOIN (SELECT s.root_session_id rid, COUNT(*) edits,
                  SUM(COALESCE(f.lines_added, 0) + COALESCE(f.lines_removed, 0)) loc
           FROM file_edit f JOIN session s ON s.id = f.session_id
           GROUP BY rid) f ON f.rid = r.id
WHERE r.id = r.root_session_id;

Every canonical table has a named correctness or product consumer; the detached search schema has one worker and one query backend. Live-lane updates touch message, session.updated_at, and the buckets through the same single-writer funnel as backfill.

Two usage features, two queries

The rethought cache exists so these service-level features are trivial reads — no feature-specific tables, just sums over usage_bucket and friends.

Activity heatmap

GitHub-style day grid for a project, a session, or everything — grouped into the viewer's timezone at query time, which only works because the buckets are hourly. The same table answers hour-of-day profiles (when do you actually work?) with a different GROUP BY.

SELECT date((b.hour_ts + :utc_offset_ms) / 1000, 'unixepoch') AS day,
       SUM(b.in_tokens + b.out_tokens + b.think_tokens
           + b.cache_r_tokens + b.cache_w_tokens) AS tokens
FROM usage_bucket b
JOIN session s ON s.id = b.session_id
WHERE s.project_id = :project AND b.hour_ts >= :since
GROUP BY day;

Contribution board

Sessions ranked by what they added to a project — tokens, commits, edits, or LOC, all sortable columns of one view. Subagent trees fold into the session the user actually ran; the per-subagent breakdown stays one query away via root_session_id.

SELECT * FROM session_contribution
WHERE project_id = :project
ORDER BY tokens DESC;   -- or commits · edits · loc
