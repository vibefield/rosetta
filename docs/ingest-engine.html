The two contracts

Everything modular hangs off two types. IngestOp is where all agent-specific weirdness ends; AgentAdapter is the one trait each agent implements. Note skim's signature: bytes in, meta out — the meta-phase promise ("no transcript body is ever fully read") is enforced by the type, because the adapter never sees a file handle.

// crates/core — the central op type; adapters end here, the writer starts here
enum IngestOp {
    SessionMeta(SessionRow),          // meta-phase upsert
    Message(MessageRow),              // one flattened timeline row
    ToolResult { tool_id: ToolId, result: String, payload: Value, is_error: bool },
                                      // a merge op, not a row — folds into its tool_use
    Usage { response: TimelineId, ts: Ms, model: ModelId, tokens: TokenSnapshot },
                                      // replacement-keyed: the writer applies (new − old) to the hour bucket;
                                      // absent components stay None — never coerced to zero
    WorkspaceObs(WorkspaceObsRow),
    FileEdit(FileEditRow),            // carries lines_added / lines_removed
    Drift(DriftFact),                 // lands aggregated (drift_agg) — never one row per bad record
}

// crates/adapter-support — one impl per agent; all agent knowledge stops at this boundary
trait AgentAdapter: Send + Sync {
    fn kind(&self) -> AgentKind;
    fn layout(&self) -> &SourceLayout;   // discovery probes with this; tests pin it to the L1 layout.toml
    fn skim(&self, head: &[u8], tail: &[u8], stat: &FileStat) -> SkimResult;
    fn parse(&self, stream: &StreamId, line: &[u8]) -> ParseOutcome;
    fn normalize(&self, rec: &ParsedRecord, ctx: &mut NormalizeCtx) -> Vec<IngestOp>;
}

Crate responsibilities

One seam per crate; each names the benches it owns. The claude-code block split and codex's cumulative→delta live in their adapters' normalize; the shared machinery (tool-merge state, ordinals, hour bucketing, root-session resolution) is agent-blind and lives in the fold.

core

purebench

Canonical row types mirroring the DDL exactly, IngestOp, blake3 id derivation, and the pure helpers: tool-merge state machine, cumulative_to_delta, hour_bucket(ts). Zero IO dependencies.

Benches: fold helpers (ops/sec), id derivation. Types first — everything depends on them.

adapters/<agent>

purebench

The existing permissive raw parsers gain the AgentAdapter impl: skim + normalize on top of parse_line. All nine crates exist; claude-code and codex go first.

Tests: replay suite extends with a golden-ops lane — fixture corpus → ops → committed JSON snapshot, pinning L2 semantics the way L1 pins schemas. Benches: parse throughput (lines/sec) per adapter.

capture

iobench

Three modules: discovery (walk layouts, stat, emit DiscoveredRuntime), watcher (notify-based, behind a SourceEvents trait — FS watching is the flakiest OS surface we touch, so tests inject synthetic event streams), ledger (append-only raw segments; the durable copy that survives agents GC-ing their own data — claude-code sweeps at 30 days).

Ports: spaghetti's append-delimited tailer — checkpoint = generation · file identity · committed offset · boundary anchor · decoder version — plus its adversarial tests (partial tails, truncation, same-size rewrites, atomic replacement, corrupted cursors, bounded IO), and the watch-before-scan / polling-fallback recovery rules. Benches: ledger append/scan (MB/sec), discovery walk (dirs/sec).

pipeline

pureio

The phase orchestrators (discover(), meta_ingest(), stream()), the priority scheduler (live ▸ on-open ▸ newest-first backfill), cursor management, and instrument — the profiler that ships in the binary. The scheduler also runs a low-duty-cycle audit lane: rotating forced verification that opens the file and checks the checkpoint anchor even when size+mtime are unchanged — a missed same-size rewrite must not stay invisible forever.

Seams: phases take &dyn deps, so integration tests run whole phases against a temp-dir corpus and an in-memory store. The fold itself stays pure.

store

iobench

schema.rs (the DDL, stamped with schema_version — on mismatch the projection rebuilds from the ledger instead of migrating; rule 4 as code, migrations never exist), writer.rs (single thread, bounded channel of batches, same-tx rows+FTS+buckets), queries.rs (typed functions for heatmap / contribution / timeline / FTS — consumers never hand-write SQL), hot.rs (the in-process tier below: metadata mirror + result caches, mutated only by the writer thread). The writer has two modes: live (rows + FTS + coalesced bucket corrections in one tx) and cold backfill/rebuild (project each source's first generation directly into the private database, defer FTS and selected indexes, build + validate once, then publish search readiness — spaghetti's 166× recovery came from exactly this, not parser parallelism).

Benches: writer rows/sec across batch sizes; query latency on a generated multi-million-row DB.

bench-corpus

bench

The load-bearing fixture. A seeded, deterministic generator synthesizing realistic corpora from the ground-truth shapes — line templates derived from fixtures, parameterized by sessions × lines × tool-call ratio, laid out on disk per the agent's real layout.

bench-corpus gen claude-code --sessions 2000 --lines 1M --seed 42 — same corpus on every machine, per iron rule 3. The 3.9GB organic corpus stays an opt-in local validation lane (the probe_local precedent), never load-bearing.

protocol · server · rosettad

io

The L3 edges: wire contract (ts-rs generated types), axum server over store::queries + store::hot, the server::hub pub/sub fan-out (topics = cache keys), and the daemon/CLI — including the profiling entry points rosettad ingest --once --profile and rosettad rebuild --profile. API pagination cursors bind an exact commit watermark — match or expired, never silently rebased; their tests must mutate rows between pages, not just insert.

Async lives only here. The ingest engine below is synchronous threads.

Runtime shape — the stream phase

"Many parallel processes" with one honest constraint: parse workers parallelize freely, writes funnel through a single writer with batched commits — that funnel is what lets lanes run without contending on SQLite locks, and what makes the same-transaction guarantee possible. Queue depths are instrumented at every arrow: the depth tells you which stage is the bottleneck.

The hot tier — in-process memory, not a cache server

Some reads shouldn't touch the DB. But rosetta is one local daemon, so the answer is an in-process tier inside rosettad — redis-like in its keyspace, pub/sub, and invalidation discipline, never an external cache server (a socket hop + serialization would be slower than the SQLite read it replaces). Two structural advantages make it clean: the single writer sees every mutation, so all invalidation is event-driven and precise — TTLs appear only for resource eviction, never correctness; and deterministic blake3 ids make ahead-of-DB serving safe, because a crash + ledger replay reproduces identical rows, so at-least-once delivery is idempotent for clients keyed by timeline_id.

tail rings

ahead of db

Ring buffer of mutations — row upserts tagged with mutation_seq, so appends AND merges into earlier rows both flow through it — per active session (~256 / 1MB cap), fed at the fold before the batch commits. The live chat view serves from here; it cannot be a DB read, because the commit cadence is slower than the latency budget.

Overflow / lagging subscriber: epoch invalidated → replacement snapshot + resync barrier. Eviction: idle ~10 min → drop the ring (the one legitimate TTL — resource-bound, not correctness); rewarms lazily on subscribe. Day one.

metadata mirror

behind db

The whole session + project metadata surface, fully resident (10k sessions ≈ a few MB — no LRU, no eviction), applied by the writer after each commit. List/browse reads never touch the DB, and the mirror doubles as the diff source for pub/sub: old row vs new row → precise events ("stream_state → indexed"), which is what makes live-reordering lists cheap.

Warm-up: one query during meta ingest. Day one — the only convenience-over-bench-gating call in this design.

result caches

behind dbbench-gated

Heatmap / contribution results keyed project:{id}:heat:{tz}:{range}, LRU-capped (~32MB). Invalidation by epoch: any bucket write for project P bumps P's usage epoch; mismatch → lazy recompute (milliseconds anyway). Live heatmaps skip the server entirely — push UsageDelta events and let the client patch today's cell.

Phase 2: added only when a profile shows these reads actually hurting.

DB-only, deliberately

io

Timeline scrollback stays on SQLite — the page cache + mmap are already a very good LRU; tune cache_size/mmap_size before writing any app-level paging cache. FTS is never cached: long-tail queries make result caching a hit-rate lie. And no external cache server, ever — it loses on every axis for a single-machine daemon.

Rule: hot-tier structures are mutated only by the writer thread — coherence by construction; readers go through snapshots that never block the writer.

Measurement — fixtures and profilers as first-class citizens

The rule: nothing performance-critical exists without a reproducible way to measure it. Three instruments cover everything.

Synthetic corpus, seeded

L1 fixtures are correctness-sized (dozens of lines); performance needs millions, and iron rule 3 forbids depending on anyone's organic data. bench-corpus generates the load deterministically from ground-truth shapes — every bench and profile run sees the same corpus on every machine.

Criterion benches live in each crate's benches/, fed by it: parse, fold, writer, queries, ledger, discovery.

The profiler ships in the binary

pipeline::instrument wraps every phase and lane: timings, rows/sec, bytes/sec, batch commit latency, queue depths. Surfaced as tracing spans for flamegraphs and as a plain table from rosettad ingest --once --profile pointed at a corpus dir — a one-command, reproducible end-to-end profile of discover / meta / stream.

Two harnesses, one headline

A live-latency harness appends synthetic lines to a watched file and measures event→row-visible p50/p95 — the realtime chat view's number. And rosettad rebuild --profile (drop DB, replay ledger) is the headline macro-bench: if rebuild gets slow, "disposable projection" quietly dies.

CI runs benches in smoke mode (--test) so they always compile and run; timing gates stay local (criterion baselines + a committed BENCHMARKS.md of reference numbers) — shared runners make timing gates flaky liars.

Measured performance and search-finalization specification

Status: partly implemented and evidence-backed. The frozen FTS campaign harness and L3 search/readiness contract exist; asynchronous search publication and an alternate backend remain gated proposals. This section records the 2026-08-26 organic validation lane, identifies measurements versus estimates, and specifies the crash-safe seams required before search can be detached from canonical publication. It updates the earlier FTS5 default without turning a local corpus into CI ground truth.

Decision boundary. Keep the raw ledger as durable truth and SQLite as the only canonical relational projection. Split canonical-ready from search-ready; evaluate a disposable search index owned by the same projection epoch. Tantivy is a benchmark candidate, not a selected dependency. No optimization below may weaken generation reconciliation, ledger replay, fail-closed schema handling, or the invariant that canonical state is recoverable without the search artifact.

Required readiness vocabulary

Every CLI/API/profile must use these terms exactly; “ingest complete” is otherwise ambiguous:

  • canonical-ready — SQLite canonical rows, usage buckets, relational indexes, generation state, quick check, and foreign keys are valid and the private file has been atomically published.
  • search-building — canonical queries are available; search returns an explicit not-ready status, never silently empty results.
  • search-catching-up — a complete base index exists but its revision is behind SQLite; an API may serve it only with an explicit stale/as-of marker.
  • search-ready — the index epoch matches SQLite and its committed revision equals the current SQLite search revision at the readiness check. Every response carries both values.
  • search-stale / failed — epoch, schema, corruption, or worker failure prevents serving; rebuild the disposable index without touching SQLite or the ledger.

The physical search directory is part of the canonical projection's derived index set, not a third truth surface: it contains no facts unavailable from SQLite, cannot rebuild SQLite, is never migrated, carries the owning projection epoch, and may be deleted at any time. The proposed dependency seam is a small search crate depending on core/store; server and rosettad depend on it, while store does not depend on Tantivy. L3 accepts one backend-neutral query contract so FTS5/Tantivy syntax never leaks onto the wire.

The search document must index timeline_id (unique term), session_id, runtime/agent, project, timestamp, message kind, content, tool input, and tool result. Filter keys live in the index; retrieving top K and filtering afterward in SQLite is ranking-incorrect. The backend returns timeline ids, scores, and matched-field information; SQLite remains responsible for authorization/filter validation and canonical row hydration. Text need not be stored twice: hydrate the top rows from SQLite and generate snippets against that text.

The L3 contract accepts structured text plus agent/runtime, project, session, time-range, kind, and error filters; it does not accept backend query syntax. Ordering is score then a stable timeline_id tie-breaker. Numerical scores are diagnostic and have no cross-backend meaning. Responses expose readiness, projection epoch, index revision, and hits so a lagging index can never masquerade as a complete empty result.

Crash-safe search coherence protocol

The existing in-memory Effects seam can wake the worker but cannot establish correctness: it is capped at 65,536 mutations and disappears on process death. Add two projection-internal structures with named consumers:

projection_state(singleton, projection_epoch, search_revision)
search_dirty(kind, key, revision, PRIMARY KEY(kind, key))

kind = timeline: reload-or-delete one complete message by timeline_id
kind = session: delete the session term and repopulate every current message
Same-commit schema rule. These tables do not land as anticipatory schema. projection_state and search_dirty, the worker that consumes and acknowledges them, and the crash/coherence tests below arrive in the same commit. Until that consumer exists, synchronous FTS5 remains the shipped implementation and neither table is justified.

projection_epoch is a new random identifier created with each whole private SQLite build and never copied across replacement; search_revision is a non-negative integer, incremented once per search-relevant SQLite transaction. The search schema version is independent of both. Readers compare all three values before serving a generation.

search_dirty is a coalesced repair set, not an event log or third representation. A search-relevant SQLite transaction increments one revision and upserts touched timeline/session keys at that revision. Cold bulk load disables dirty maintenance because the first index is a full scan. Tool-result and usage merges dirty their owning timeline; a generation sweep or project reassignment dirties the session.

  1. Commit canonical state and repair keys together. A crash cannot produce a canonical change that the worker has no way to discover.
  2. Read a bounded revision. Reload the complete current documents from a SQLite read snapshot; missing rows become deletes.
  3. Apply delete + add and commit the index. Store {projection_epoch, search_schema, revision} in the search commit metadata.
  4. Acknowledge only after search commit. Delete repair rows whose stored revision is at or below the committed watermark. A newer coalesced repair survives.

Build each full index under <projection>.search/generations/<epoch>-<schema>.tmp. After its index commit, sync the generation, atomically rename it out of .tmp, write and sync CURRENT.tmp, rename that manifest to CURRENT, and sync the parent directory. On open, reject a manifest whose commit payload differs from SQLite; retire old generations only after the new manifest is durable and no reader holds them. Verified against Tantivy 0.26.1 on 2026-08-26, Tantivy provides a multi-threaded IndexWriter with explicit durable commits; its supported update model is delete plus reinsert, readers support manual or post-commit reload, and commit metadata exposes a client payload through IndexMeta. Highlight snippets are available through its SnippetGenerator. These establish feasibility, not performance on Rosetta's corpus.

Canonical publication split

Transition constraint: today's external-content message_fts lives inside the canonical SQLite file. Extracting a Rust trait does not turn it into a disposable sidecar, and a 34-second post-publication write transaction in that same file would contend with the live writer. Until an external backend passes the gates below, the shipped default keeps synchronous FTS5. The FTS5 reference can be built in a disposable benchmark copy; it need not be a simultaneously served production index. A SQLite-only contentless FTS sidecar would be a separate candidate and must pass the same coherence, latency, and storage gates as Tantivy.

Split today's Store::finish_bulk_load into an invariant-preserving canonical gate and an independent search gate only after such a sidecar exists:

  1. Finalize canonical. Verify no staged/incomplete generation; build usage buckets and relational indexes; run ANALYZE, quick_check, and foreign-key validation.
  2. Publish canonical. Restore live pragmas, checkpoint to one file, sync, and atomically replace SQLite. This defines canonical-ready.
  3. Build search from a SQLite snapshot. Capture its epoch/revision, scan canonical messages, commit a private search generation, then drain repairs newer than the snapshot.
  4. Expose readiness. Session/observe/metrics endpoints continue serving. Search reports building/catching-up until its generation is current.

rosettad watch owns the asynchronous worker. A finite ingest command defaults to --search=wait so process exit still means fully ready; it may offer async only when handing work to a persistent daemon, and skip for explicit normalizer-development loops. Merely moving FTS after publication while the same command waits does not reduce total wall time; it only changes the readiness boundary.

Ledger cost: preserve live ordering, stage private-build durability

C The live stream path calls Ledger::flush after every written batch, and flush performs sync_data. This is mandatory when a live SQLite transaction will become visible. A brand-new private SQLite file does not need the same per-batch durability cadence, but delaying sync is safe only if its not-yet-durable ledger segments are staged outside the committed segment namespace.

existing/live projection — unchanged
append raw → flush + sync_data → SQLite transaction → visible canonical state

private cold projection — proposed
append raw → buffer-flush/rotate run-scoped staged segments → private SQLite
seal all sources → finalize/validate SQLite → fsync staged files + directory
               → promote segments + fsync runtime directory → publish SQLite

Create the stage beneath the target runtime ledger directory so promotion is a same-filesystem rename. Every rotation must explicitly flush and retain its error; the final barrier tracks and syncs all segments touched by the run, not just the current writer. To avoid exposing half a multi-segment run, extend the container layout so the scanner reads legacy root segments plus atomically committed runs/<sequence>-<run-id>/ directories and ignores .stage-*. Under the projection lock, rename the entire synced stage directory once, then sync its parent before SQLite may publish. Frame format RLG1 need not change.

Prior art — ported from spaghetti, narrowly

Spaghetti's architecture stays buried (the 31-variant fact algebra, 101 tables, DTO mirrors, durable readiness machines — its own deletion history removed 190k+ lines of it). Its reliability algorithms and their adversarial tests come along, reimplemented against the op-stream rather than copied wholesale:

  • append-delimited tailer + tests → capture. The single highest-value port: generation/identity/anchor checkpointing, truncation and same-size-rewrite detection, bounded IO — and the test suite that proves them.
  • recovery rules → capture. Watch-before-scan, notifications as hints, bounded coalescing, polling fallback — the state-machine rules, not the scheduler framework.
  • writer topology → store. Connection-owning thread, group commits, checkpoint CAS, deterministic crash seams.
  • usage normalization vectors → adapters. Response-level replacement, cumulative→delta, inclusive-cached-input split by subtraction, unknown stays unknown — ported as golden tests on pure normalize.
  • observer overflow semantics → server::hub. Epoch invalidation + replacement snapshot + resync barrier; identity never bound to delivery sequence.
  • search modes → store + L3. Cold-build vs live maintenance, readiness gating, exact-watermark cursor expiry (the catalog cursor's silent rebase was a bug — don't port that side).

Build order

Measurement infrastructure arrives before the thing it measures — the pipeline is profiled from its first day, not instrumented after the fact.

  1. core — rows + IngestOp + pure helpers. Types first; everything depends on them.
  2. store — schema + writer + queries. Benched against hand-built ops before any adapter exists.
  3. bench-corpus — claude-code + codex generators. Before the pipeline, deliberately.
  4. adapters — AgentAdapter for claude-code + codex over the existing parsers. Golden-ops snapshots pin semantics.
  5. pipeline + capture — phases, instrument, scheduler; watcher and ledger last. Backfill works without them.
  6. store::hot + server::hub — rings first (correctness), metadata mirror next; result caches stay bench-gated. Arrives with the L3 server work.
Decided — ledger-first, with an explicit crash protocol. The stream lane preserves each framed record's original bytes and durably appends them to the ledger before committing their normalized projection: extra write IO during backfill, paid deliberately, because it makes rebuild, provenance, and GC-survival unconditional. The ledger and SQLite are separate filesystems, so SQLite cannot make both atomic — the ordering does: (1) frame only complete raw records; (2) append and durably flush the ledger segment; (3) ONE SQLite transaction — CAS the driver checkpoint, then canonical rows, FTS/live indexes, bucket corrections (new − old), and drift aggregates; (4) publish committed mutations to the hub. Invariant: recovery may find an orphan ledger tail (harmless); it must never find a database reference to unflushed ledger bytes.
Decided — the projection carries no second journal. Rule 4 names TWO representations: the raw ledger (durable truth) and the projection (canonical, disposable). Everything else inside the database is projection-internal machinery — derived, same-transaction, prunable — like the FTS index. source_op is exactly that: a staging buffer holding only not-yet-active replacement generations, pruned at activation, empty in steady state. A source's first generation bypasses it inside the unpublished cold database because there is no clean contribution to protect; that database cannot publish after an abandon. Appends never journal. A swap removes the old generation's contribution via src_cursor provenance columns (messages and the small tables all carry one), renumbers the session's presentation ordinals deterministically (source path · byte offset · insertion order), and recomputes the session's usage buckets from the surviving rows — aggregates can never keep residue a swap should have removed. Drift is additive-only: what was observed stays observed. Cross-file merges into a rewritten file's rows are re-derived by a one-shot forced replay of the session's sibling files (the heal pass), not by replaying a stored op journal.
