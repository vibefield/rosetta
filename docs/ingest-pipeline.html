rosetta · layer 2 · function-level system map

The entire ingest pipeline, drawn from the Rust.

Every production ingest path — ingest, watch, serve, rebuild — is the same three phases plus a live loop that re-enters them. This page is a map of those stages down to the functions that implement them, read from the crates as of 2026-08-31. Companion to ingest-engine.html (design) and canonical-model.html (what gets stored).

rosettad pipeline capture adapters core store search server
Iron rule, as topology. Agent knowledge stops at dyn AgentAdapter. Adapters receive already-bounded bytes or already-serialized JSON rows — never a file handle, DB connection, or watcher. Capture never sees a session. Store never sees a JSONL line. Search never writes canonical rows. Two durable representations only: the checksummed raw ledger, and one canonical SQLite projection. Replacement generations, tool correlations, and late usage reconcile in process RAM; no serialized op journal or pending-merge table is a third store.

System overview

Data flows up only. L1 is evidence, not runtime. Consumers never reach past L3 into the store.

representation 1

Raw ledger

<db>.ledger/<agent>/ size-rotated blake3 frames. Precious. Agents GC their own files; this is the replay substrate. Cold first ingest stages it privately, then atomically promotes.

representation 2

Canonical projection

SQLite schema 13 plus content-addressed <db>.assets/ members. Disposable. Store::apply is the only row writer. On schema/normalizer bump, rebuild from the ledger—never migrate.

not a representation

FTS5 sidecar

<db>.search/ is independently disposable. Canonical lists stay up while it builds. Loss never blocks canonical reads.

Command paths

rosettad::main dispatches eight verbs. All ingest verbs take the same projection_lock (SQLite exclusive on <db>.lock) so two writers cannot share a projection.

Probe every registered adapter’s data root. Nothing is ingested. The app shows the census; the user (or CLI) flips agent_runtime.enabled.

Document and SQLite snapshots

Virtual sources physical#native_id have ordinary cursors and generations. Every pass hashes full content — audit by construction. Document and SQLite meet in apply_snapshot_records so health, ledger order, and sweeps cannot diverge.

document.rs

stream_document_sources

Group by physical path. snapshot_document until Ready / Missing / Oversized / Unstable×retries. Per virtual: document_records then apply_snapshot_records. A fully missing physical source with source_missing tombstones runs an empty generation so old rows are swept.

snapshot.rs

stream_snapshot_sources

Group by db. db_stamp cheap skip is not used for content identity — every pass copies once (snapshot_db) and runs the adapter’s declared SQL. Rows become {"query":name,"row":…} JSON records. WAL content not yet checkpointed is visible.

pipeline apply_snapshot_records
revision = blake3(records joined by \n)
if checkpoint.snapshot_revision matches AND active generation matches → maybe stamp-only CAS, skip rewrite
else new generation = max(highest, active)+1
ledger.append_raw(index-as-offset, record bytes) · checkpoint
fresh NormalizeCtx, restore_state(None)
for record: ingest_line; chunk at 512 ops via flush_chunk
last chunk: seal_generation → Ledger::complete_generation then Activate/Abandon
empty records (deleted membership): still seal + flush so the sweep happens
Tombstones: physical file gone → SessionFile.source_missing=true, empty generation is authoritative. Member removed from a still-present snapshot → extra virtual file, source_missing=false, empty/new records sweep that member. A racing ordinary Missing read of a non-tombstone stays incomplete and keeps the last clean projection.

Store open modes

open / open_progressive

Live completed file, or legacy disk-progressive audit/resume. A completed app boot stays live and performs only incremental catch-up.

open_shared_in_memory_for_rebuild

Normal fresh app. Exact canonical schema in named RAM, metadata/timelines readable through ProjectionReader, aggregates gated.

open_for_rebuild / open_for_backfill

Empty file only. Deferred indexes. Finalization refuses if any generation was abandoned.

Ledger protocol

Self-describing size-rotated segments. Default root <projection>.ledger/<agent>. A missing projection beside an unmarked existing ledger normally fails closed to rebuild so generations cannot collide. Fresh app serve instead owns a named <ledger>.staged tree with a durable manifest and resumes that generation automatically.

5 · Live lane

Deliberately built on top of the two existing phases. A change hint re-runs meta when a new claimed file appears, and stream over just the changed subset otherwise. Events are hints; the tailer checkpoint decides what happened.

Fresh RAM serve

The listener exists first and consent precedes source reads. Canonical metadata and closed timelines are progressive in named shared memory; the ledger and validated SQLite file are the only durable publication. Global aggregates and detached search wait for that publication.

Rebuild from the ledger

Drop the projection, replay the ledger. Two streaming passes. Deterministic ids make an interrupted rebuild converge when rerun.

Search sidecar

Canonical and search readiness are independent. The worker builds private immutable generations and atomically selects one with CURRENT. Acknowledgements are epoch-scoped so a stale worker cannot erase a newer projection’s repairs.

Hot tier, after commit

Not durable. Rebuilt from the projection on restart. The hub is a transport fan-out, not a second store.

store::hot

TailRings · MetaMirror · Effects

observe_effects starts collecting. drain_effects after each live batch. Mutations: Message, ToolResult, Usage, SessionSwept. Overflow or dead epoch → Replay::Expired → replacement snapshot.

server::hub

Hub::absorb · absorb_meta · warm

Session topics get the mutation log; /ws/meta gets precise metadata diffs from the writer. rewarm is a recovery/equivalence operation, not a timed cold poll. ConsentGate and BoostLedger sit on the HTTP side.

Adapter boundary

Object-safe. One implementation per agent. Layout inventory is broader than the driven streams — undeclared files stay inventory, never accidental transcripts.
