rosetta · runtime · time sequence

What runs, in what order, on which thread

Product path: Electron spawns rosettad serve, the writer thread ingests, Tokio serves HTTP/WS, a detached thread builds FTS, and the History room reads only L3. Finite ingest is the same pipeline without a listener. Function names are from the current tree. Design: ingest-engine.html. Call graph: ingest-pipeline.html.

One synchronous writer owns SQLite. Tokio never applies a batch. Search never writes the canonical file. The app never opens the projection. During cold load, the only fan-out to the UI is a 500 ms read-only Hub::rewarm plus /api/status meters. After canonical_ready, live ticks drain Effects into Hub::absorb.
Writer (main) — discover, meta, stream, apply, live ticks Tokio — bind, axum, 500 ms rewarm, signals Search thread — FTS5 sidecar App — Electron + React over HTTP/WS Filesystem — agent homes, ledger, notify

Inside one file — ingest_file

pipeline/src/stream.rs. JSONL only; document/SQLite snapshot drivers take sibling functions after the tail queue drains. Ledger bytes are durable before the projection transaction.

  1. cursor_row — load or insert ingest_cursor for (runtime, stream, path).
  2. PipeCheckpoint::decode — resume only if session, stream, normalizer_version, and source_generation == active_generation. Otherwise replay from byte zero (RAM join state is not on disk).
  3. AgentAdapter::restore_state — adapter-private cursor (Claude response map, etc.).
  4. Loop: Tailer::read(path, tail, force_replay) → TailRead::Batch of framed records (or Missing / Retry / oversized).
  5. On generation restart: bump generation, reset ordinal/usage/state, generations_restarted++.
  6. For each TailItem::Record: adapter.ingest_line(&mut NormalizeCtx, stream_id, payload) → parse + normalize (one function; not separately timed). Emits Vec<IngestOp>.
  7. Build PipeCheckpoint + SourceMode: Append if same generation; Activate if complete+clean replacement; Abandon if complete+dirty; else Stage (RAM, not published).
  8. Ledger::append_raw then optional complete_generation, then checkpoint (not a full fsync every batch — durability barrier is later).
  9. Store::apply(Batch { ops, checkpoints, source }) — one transaction, CAS on the cursor blob.
  10. If !batch.more_available, break. Sibling-heal: if this file restarted a generation, replay other files in the same session.

What is allowed to run in parallel

Yes, concurrently

Axum handlers vs the writer (read-only SQLite / hub mutex). Rewarm spawn_blocking opens a second read-only connection every 500 ms during backfill. Search worker reads the canonical file, writes only the sidecar. App HTTP/WS. Filesystem notify queue. Ctrl-c watcher.

Never concurrently

Two Store::apply calls. Two writers on one projection (file lock in projection_lock). Tokio applying batches. Search acknowledging its own revision (the writer thread calls acknowledge_search). Meta ingest of runtime B before runtime A’s skim has committed — skims are sequential on the writer so lists appear as a whole roster.

Crash and resume rules (why the order is that order)

  1. An orphan ledger tail is harmless; a projection row without flushed raw bytes is not — hence ledger-before-apply.
  2. A process exit drops the RAM tool accumulator. Resume replays the generation from byte zero instead of reading a SQLite journal that no longer exists.
  3. Checkpoint CAS (expected blob) makes two writers on one cursor fail closed.
  4. Progressive first-run commits are public and resumable; finite ingest publishes atomically after validation.
  5. Search epoch must match projection epoch; a sidecar from another rebuild is never serveable.
  6. Effects are observed only after canonical_ready, so the hub never fans a half-built live ring during cold load — lists move via rewarm instead.
